# 전체 재점검 P2 개선 결과 — 2026-10-07

재점검에서 확인한 P2 7건을 수정하고 Supabase 서버에 백업·복원 기능을 적용했다. 이번 재점검에서 새로 확인된 P1은 없다. 아래 P3와 추가 기능 제안은 후속 작업으로 남긴다.

## 수정한 사항

| 번호 | 기존 문제 | 개선 결과 |
| --- | --- | --- |
| A01 | 메뉴를 옮기면 작성 중인 종목·포지션·거래·계산·설정 입력이 사라짐 | 로그인한 화면 안에서 메뉴별 작성 내용을 보존하고 돌아오면 복원한다. 저장 재시도 식별자도 유지한다. 같은 메뉴를 다시 누르면 화면을 재생성하지 않는다. |
| A02 | 부분 매도 후 카드 수익률과 대시보드 총손익의 기준이 달랐음 | 카드 수익률을 실현손익과 평가손익을 합한 총손익 / 최초 매수금액으로 맞췄다. 표시 이름은 ‘총 수익률’이다. |
| A03 | 오래 열린 설정 화면에서 저장하면 다른 컴퓨터에서 변경한 설정까지 되돌림 | 사용자가 바꾼 항목만 저장한다. 손대지 않은 항목은 서버의 최신 값을 반영하고, 저장 도중 새로 작성한 입력도 유지한다. |
| A04 | 서버에 설정·기록만 있는 계정에도 이전 로컬 자료 가져오기를 제안함 | 서버 문서가 하나라도 있으면 기존 서버 자료로 진입한다. 서버가 비어 있을 때만 로컬 자료 가져오기를 제안한다. |
| A05 | 브라우저 저장소 접근이 막히면 정상 서버 로그인까지 중단됨 | 이전 로컬 자료 읽기 실패를 별도로 처리해 서버 계정 사용을 계속한다. 읽을 수 없는 로컬 자료는 가져오기를 중단하고 안내한다. |
| A06 | 시세 서버 제한·인증·장애가 ‘검색 결과 없음’으로 표시됨 | 요청 제한, 로그인 필요, 서버 장애를 구분해 안내한다. 검색 실패와 실제 검색 결과 없음도 구분한다. |
| A07 | 현재 서버 자료의 내보내기·복원·정기 보관 기능이 없음 | 계정별 서버 백업, JSON 파일 다운로드, 내용 확인 후 복원, 일별 자동 보관을 추가했다. 복원 전 자료도 보관한다. |

메뉴별 작성 내용은 현재 열린 로그인 화면의 메모리에 보존한다. 브라우저 새로고침·종료 후 보존하는 기능은 아니다. 로그아웃과 전체 자료 복원 시 작성 내용은 비워 다음 계정이나 복원된 자료와 섞이지 않게 한다. 저장한 업무 자료의 기준은 계속 서버다.

수익률 예: 10주를 $10에 매수하고 9주를 $20에 매도한 뒤 남은 1주의 현재가가 $10이면, 총손익은 +$90이고 총 수익률은 90%다. 현재가가 없어 남은 수량의 평가손익을 계산할 수 없으면 총 수익률을 임의로 계산하지 않는다.

## 백업·복원 사용 방법

**설정 → 자료 백업·복원**에서 다음 기능을 사용한다.

1. **현재 자료 내려받기**: 서버의 최신 종목·포지션·매도 기록·설정·계산 기록을 JSON 파일로 저장한다.
2. **서버에 백업 보관**: 현재 계정 자료를 서버에 직접 보관한다.
3. 보관된 서버 백업 또는 내려받은 파일을 선택해 복원 내용을 확인한다.
4. 종목·포지션·매도 기록·계산 기록 개수를 확인하고 **이 백업으로 복원**을 누른다. 기존 계정 자료 전체가 교체되며, 복원 직전 자료는 서버 백업으로 남는다.

서버 자동 백업은 자료가 있는 계정의 UTC 날짜별 첫 변경 직전 상태를 보관한다. 한국 시각의 날짜 경계는 오전 9시다. 변경이 없는 날에는 추가로 만들지 않으며, 기능을 적용한 직후 모든 기존 계정의 백업을 일괄 생성하지는 않는다. 바로 백업을 남기려면 직접 보관 버튼을 누르면 된다.

계정별 최대 20개를 보관하며, 총 자료 크기가 약 36MiB를 넘으면 오래된 백업부터 정리한다. 최신 두 개는 유지한다. 서버 백업 자료 하나의 한도는 16MiB이며 업로드할 파일도 16MiB 이하여야 한다. 계정 비밀번호, 로그인 세션, 서버 API 비밀 키는 백업 파일에 포함하지 않는다.

복원 미리보기 이후 다른 컴퓨터에서 자료가 바뀌면 복원을 중단하고 다시 확인하도록 한다. 복원은 종목·설정·계산 기록을 한 번에 처리하며, 응답이 끊겨 재시도해도 같은 복원이 중복 실행되지 않는다. 다른 계정의 백업 조회와 직접 백업 쓰기·삭제는 허용하지 않는다.

서버 백업은 같은 Supabase 프로젝트 안에 보관하는 앱 자료 백업이다. 프로젝트 전체의 외부 재해 복구 백업은 아니다. 중요한 시점의 내려받은 파일은 OneDrive 등 별도 장소에도 보관할 수 있다.

## 검증 결과

- 기존 도메인·시세 검증 25건, 포트폴리오 검증 41건, 기존 P2 검증 17건 통과.
- 새 P2 브라우저 검증 10개 묶음 통과: 메뉴 입력 보존, 부분 매도 수익률, 컴퓨터 간 설정 충돌, 저장 중 입력, 부분 서버 자료, 저장소 차단, 시세 오류, 백업 내보내기, 복원 충돌·재시도, 손상 파일·좁은 화면·계정 전환.
- 공식 Supabase SDK를 사용하는 로그인·회원가입·서버 저장 브라우저 검증 통과.
- PostgreSQL 로컬 검증 통과: 기존 저장 기능, 계정 분리, 자동·수동 백업, 복원 전 보관, 전체 복원의 원자성, 버전 충돌, 중복 방지, 잘못된 자료 거부, 최대 20개 보관.
- 실제 Supabase 서버 검증 통과: 백업 권한, 계정 분리, 일별 보관, 복원 충돌, 복원 중복 방지, 복원 전 보관. 임시 계정과 자료는 단일 트랜잭션 안에서 검증 후 롤백했으며 기존 이용자 자료를 읽거나 변경하지 않았다.
- 실제 공개 API에서 로그인하지 않은 백업 표·백업/복원 함수 접근이 거부됨을 확인했다. 시세 함수의 인증·출처·메서드 검사도 통과했다.
- 수정 JavaScript 문법 검사와 변경 파일 공백 검사 통과. 백업 화면을 600×300의 좁은 화면과 일반 데스크톱 크기에서 확인했다.

서버 마이그레이션: `20261007104227_account_snapshots.sql`. 새 기능의 접근 권한과 계정별 필터를 적용했다. 서버 성능 점검에는 지적 사항이 없었다. 보안 점검에는 기존 유출 비밀번호 차단 미설정 경고와 내부 표의 정책 없음 안내 두 건이 남아 있다. 내부 표는 직접 접근을 차단하도록 의도한 구조다. 유출 비밀번호 차단은 현재 무료 요금제에서 제공되지 않는 기능이므로 이번 작업에서 요금제를 변경하지 않았다. [Supabase 비밀번호 보안 안내](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection), [내부 표 정책 점검 안내](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy).

서로 분리된 브라우저 환경에서 변경·동기화를 재현했다. 실제 이용자의 비밀번호를 사용하거나 다른 물리적 컴퓨터에서 시험하지는 않았다.

## 추가 기능 추천

1. **삭제 취소**: 삭제한 종목·포지션·매도 기록을 잠시 되돌리거나 최근 삭제함에서 복구. 이번 전체 백업 복원보다 일상적인 오조작에 빠르게 대응할 수 있어 가장 먼저 추천한다.
2. **거래내역 CSV 내보내기와 기간별 실현손익**: 종목별·월별 거래를 엑셀로 확인하고 매도 성과를 비교. 날짜 범위와 통화별 합계를 먼저 제공하는 것이 적합하다.
3. **수수료를 반영한 손익**: 거래마다 수수료를 입력하고 총손익에 반영. 서로 다른 통화를 합산할 때는 환율과 기준 시점을 명확하게 선택하는 단계가 필요하다.
4. **계정 내 비밀번호 변경**: 소규모 이용자도 다른 사람의 도움 없이 계정을 관리할 수 있도록 간단한 설정 항목부터 추가한다.

위 추가 기능과 P3는 이번 P2 수정에 포함하지 않았다.

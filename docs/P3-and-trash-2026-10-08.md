휴지통과 P3 6건의 코드 개선을 적용했다. P3 중 5건은 개선·검증을 완료했고, A08은 비밀번호 변경과 복구 화면을 구현·검증했으나 실제 복구 메일 발송을 위한 SMTP 설정이 남아 있다. 사용자가 현재 미설정이라고 확인했다. 회원가입 시 이메일 인증을 생략하는 기존 선택은 유지한다.

## 휴지통 사용

좌측 **휴지통** 메뉴에서 삭제 항목을 확인하고 **복원**, **영구 삭제**, **휴지통 비우기**를 사용한다. 종목, 포지션, 매도 기록, 계산 기록을 보관하며, 종목·포지션을 삭제할 때 하위 기록은 원래 항목 안에 함께 보관한다. 계산 기록 전체 삭제는 한 묶음으로 보관한다. 기능 적용 이전에 삭제한 항목은 소급해서 생성하지 않는다.

삭제 원본 보관과 활성 자료 변경은 같은 서버 트랜잭션으로 처리한다. 보관에 실패하면 삭제도 하지 않는다. **보관기한은 삭제 시각부터 한국 날짜의 달력 기준 6개월**이며 항목별 복원 기한을 표시한다. 기한이 지나면 서버에서 조회·복원을 차단하고 매시간 자동 정리한다. 새로운 삭제를 보관하기 전에도 해당 계정의 만료 항목을 정리한다. 기존 휴지통 항목에도 원래 삭제 시각을 기준으로 적용한다. 계정별 최대 200개·20MiB를 허용하며, 아직 기한이 남은 항목으로 한도를 넘으면 삭제를 중단하고 불필요한 항목을 영구 삭제하도록 안내한다.

복원은 최신 자료에 해당 항목만 추가한다. 원래 종목·포지션이 없으면 상위 항목을 먼저 복원하도록 안내하고, 동일 ID가 있거나 복원할 매도 기록이 현재 매수 수량을 초과하면 중단한다. 포지션 번호가 충돌하면 새 번호를 배정하며 수량·실현손익·상태를 다시 계산한다. 복원과 휴지통 제거는 한 번에 처리하고 동일 요청의 재시도는 중복 실행하지 않는다.

휴지통은 계정별 서버 자료다. 다른 계정은 조회·복원·삭제할 수 없다. **영구 삭제**는 휴지통에서 해당 항목을 제거하는 기능이며, 별도로 보관한 전체 백업 파일이나 서버 백업까지 제거하지는 않는다. 전체 백업 복원은 기존 ‘복원 전 자료’ 백업으로 보호하며, 이 과정의 교체 항목을 휴지통에 중복 생성하지 않는다. 현재 백업 파일에는 활성 종목·설정·계산 기록이 포함되고 휴지통은 포함되지 않는다.

서버 적용 파일: `20261008085344_trash_and_incremental_reads.sql`. 성능 점검의 지적 사항은 없었다. 기존 유출 비밀번호 차단 미설정 경고는 무료 요금제 제약이며, 직접 접근을 막는 내부 표 두 개의 정책 없음 안내는 의도된 구조다. [비밀번호 보안 안내](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection), [내부 표 정책 안내](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy).

6개월 보관기한은 `20261008105550_trash_six_month_retention.sql`로 추가 적용했다. Supabase Cron의 `silver-trash-retention` 작업은 매시간 만료된 휴지통 항목만 삭제하며 일반 이용자는 정리 작업을 호출하거나 변경할 수 없다. 실제 서버에서 합성 계정으로 만료 항목 조회·복원 차단, 정상 복원·재시도, 월말·윤년·한국 날짜와 조회 시간대 일치, 만료 항목 용량 정리 및 활성 자료 보존을 확인하고 검사 자료를 롤백했다. 적용 당시 실제 휴지통은 비어 있어 삭제된 기존 항목은 없다. 보안 점검에 새 지적 사항은 없으며, 새 만료 시각 인덱스의 아직 사용되지 않았다는 정보는 정리 작업을 위한 인덱스이므로 유지한다. [미사용 인덱스 안내](https://supabase.com/docs/guides/database/database-linter?lint=0005_unused_index).

배포 검증에서 서버 연결을 끈 로컬 방식의 창 간 저장 지연을 재현했다. 브라우저 잠금만으로는 다른 창의 최신 저장 원본이 즉시 보인다고 보장할 수 없어, 로컬 모드에서만 마지막 저장의 SHA-256 값을 IndexedDB에 확인하고 일치할 때 수정하도록 보호했다. 이 확인 자료에 업무 원본을 보관하지 않으며 운영 서버 저장 경로는 사용하지 않는다. 불일치가 계속되면 입력을 유지하고 저장을 거부한다. 두 창의 동시 포지션 20개 저장을 12회 반복해 누락·중복 없이 통과했다. [Web Storage 표준](https://html.spec.whatwg.org/multipage/webstorage.html#the-localstorage-attribute).

## 비밀번호 복구 메일의 남은 설정

[Supabase 메일 설정](https://supabase.com/dashboard/project/pyerygphflowylaqtpht/auth/smtp)에서 외부 SMTP를 활성화하고 발신 주소·이름, 서버 주소·포트, 사용자 이름·발송 비밀번호를 직접 입력해야 한다. 비밀 값은 채팅·코드·보고서에 넣지 않는다. Supabase 기본 SMTP는 프로젝트 팀원 외 주소로 발송을 거부하므로 일반 이용자의 분실 복구를 완료할 수 없다. [공식 SMTP 안내](https://supabase.com/docs/guides/auth/auth-smtp).

저장 후 로그인 화면에서 본인이 관리하는 시험용 계정의 복구 메일 요청 → 메일 링크 → 새 비밀번호 설정 → 새 비밀번호 로그인까지 확인한다. 프로젝트 Site URL은 `https://ssb4107-cyber.github.io/trade-calculater/`로 유지한다. 별도의 메일 공급자 계정·발신 인증이 필요한 경우 해당 설정도 먼저 완료해야 한다. 이메일 인증 없이 즉시 회원가입하는 기능과 로그인 상태의 비밀번호 변경은 이 메일 설정과 별개다.
